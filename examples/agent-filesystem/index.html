A cloud filesystem for agents

Plan · Jun 2, 2026

Agents today are amnesiac. Every session starts from nothing, ends with nothing, and cannot hand its work to the next agent or to the same agent on another machine. A persistent cloud filesystem that agents can read and write closes that gap. It turns a stateless call into something with continuity.

There is a second gap underneath it. A drive that agents read and write is, today, invisible to people. There is no good way to see what an agent stored, browse it, trust it, or share it. That is a design problem, not an infrastructure problem, and it is the part worth building: a clear human window onto the agent filesystem.

The goal here is a polished, working prototype, scoped tightly. Single user, no billing, no abuse machinery. Depth of craft on a narrow slice over breadth.

The north star

You hand an agent a task. It writes files into a cloud drive as it works. You watch them appear live: folders filling in, a report rendering, an image dropping in, each tagged with which agent wrote it and when. Then you click a folder and publish it to a public URL.

Everything is designed backward from that one minute. Realtime, provenance, and preview are the hero. Everything else is supporting cast.

Architecture

The drive

Backend

Rent the infrastructure, do not build it.

  • Supabase as the minimal drive: Postgres for file metadata (path, agent, session, timestamps, type), Storage for the bytes, Realtime for live updates, Auth as a simple gate.
  • One service, near zero ops, and Realtime gives the live writing feel for free.
  • Alternative: ride an existing agent drive if its API is open. More on brand, less control over polish.

The agent interface

MCP server

The part that makes it real, not a mockup.

  • A small TypeScript MCP server exposing fs_list, fs_read, fs_write, fs_delete, fs_publish.
  • Connect it to Claude Code or Claude Desktop so a real agent can read and write the drive.
  • Every write records who wrote it: which agent, which session.

The window

Web app

Where most of the effort goes. This is the craft.

  • Next.js and React, subscribed to the drive's realtime feed.
  • Browse the tree, preview files, see an activity timeline of what changed and by whom.
  • Publish any folder as a public site. That last step is the existing weblink tool, so the whole arc closes on itself.

Phases

Define and design

Phase 0

Lock the demo and the signature idea.

  • Lock the demo narrative and design the key screens: drive browser, file preview, activity timeline, publish flow.
  • Pick the one novel thing to explore: agent provenance. How do you show that an agent, not a person, wrote this file, in which session? That is unclaimed design territory. Make it the signature.

Write path

Phase 1

Prove read and write, headless.

  • Supabase schema plus the MCP server.
  • Success: a real agent session writes a file and it lands in the drive with full metadata. No UI yet.

The live window

Phase 2

The hero moment.

  • A read only browser of the drive with a realtime subscription.
  • Run an agent, watch files stream in. Get the motion and the feel right here.

Previews and provenance

Phase 3

Make it sing.

  • Great file viewers: markdown, syntax highlighted code, images, live HTML.
  • The activity timeline: who or what wrote what, and when. Empty states, motion, taste.

Publish a folder

Phase 4

Close the arc.

  • Wire fs_publish to weblink. A folder becomes a public URL.

First move

  • Spend ten minutes checking whether an existing agent drive exposes an open API. If it does, you may skip building any backend and point the window straight at it.
  • If it does not, Supabase is the minimal drive, and Phase 1 begins.
